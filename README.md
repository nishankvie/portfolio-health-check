# Portfolio Health Check

A Streamlit app that turns a messy venture capital portfolio export into a clean dataset, risk metrics, traffic-light flags, Monte Carlo simulations, a machine-learning early warning and a monthly update.
A separate module values an Austrian company pension plan with the projected unit credit method.
Every number is calculated by code you can read, and every formula is shown in the app.

**Live app:** _link coming soon_

> **All data is synthetic.** The 15 startups and 41 employees are fictional, with invented names, and every number was generated by `src/generate_data.py` and `src/pension.py`. Nothing here describes a real company or person. Machine-learning results only demonstrate the method.

## Quick start

You need Python 3.11 or newer.

```bash
pip install -r requirements.txt
streamlit run app.py
```

Your browser opens at `http://localhost:8501`. Use the sidebar to switch between the five pages.

The sample data is already in `data/`. To regenerate it or run each step in the terminal (run from the project folder):

```bash
python3 src/generate_data.py   # creates the synthetic portfolio (truth + messy raw file)
python3 src/clean.py           # cleans it and scores the result against the truth
python3 src/metrics.py         # rolling flags and the warning backtest
python3 src/simulate.py        # Monte Carlo scenarios
python3 -m src.ml_model        # rules vs logistic regression vs random forest
python3 -m src.report          # writes reports/portfolio_update_YYYY-MM.md
python3 -m src.pension         # pension DBO, sensitivities and Monte Carlo
```

The last three use `-m` because they import other modules from `src/`.

## Data cleaning page

### What it's for

Real portfolio data arrives as spreadsheet exports with typos, mixed formats, duplicates and gaps. Before any metric can be trusted, the data has to be cleaned, and every change has to be traceable. The cleaner follows one principle:

> **Fix what's safe, flag what isn't, log everything.**

- **Fix** when the correct value is certain (e.g. `€12.345` is clearly 12,345 euros).
- **Recalculate** when other columns determine the value exactly.
- **Estimate** only where neighbouring months carry real information, and mark the result as estimated.
- **Flag** when the code can't know the right answer.
- **Log** every change with the old value, the new value and the reason.

### Controls

| Control | What it does |
|---|---|
| **Upload a raw portfolio CSV** | Cleans your file and replaces the sample data everywhere in the app. If required columns are missing, a red error lists them and the previous data stays. |
| **Reset to sample data** | Goes back to `data/raw_portfolio.csv`. |
| **Metric cards** | Rows in, rows out, total fixes (log entries) and estimated values. |
| **Tabs** | Raw data, Cleaned data, and Cleaning log. |
| **Filter by issue** | Shows only one type of log entry, e.g. "accounting mismatch". |
| **Download buttons** | Save the cleaned CSV and the cleaning log. |

### Every issue the cleaner handles

The sample file has 362 rows. The cleaner returns 360 (15 companies × 24 months) and writes 104 log entries.

| Issue | Example | What the cleaner does | Type | Count in sample |
|---|---|---|---|---|

| Date format | `01.01.2025` next to `2025-01-01` | Parses ISO first, then `dd.mm.yyyy` for the rest (Austrian convention) | Fix | 20 |
| Suspicious date | not the 1st of a month, or outside the data period | Logged for review, not changed | Flag | 0 |
| Text number | `€42.474` (Austrian thousands dot) | Converts to 42474 | Fix | 20 |
| Exact duplicate | the same row twice | Drops the copy | Fix | 10 |
| Conflicting duplicate | same company and month, different numbers | Keeps the first, logs the rest for review | Flag | 0 |
| Negative headcount | `-54` | Blanks it (we can't know the true value), then estimates it like any gap | Fix + estimate | 3 |
| Accounting mismatch | revenue entered 100× too high | Recalculates revenue from costs and net burn | Recalculate | 2 |
| Missing revenue | empty cell, costs and burn present | Recalculates revenue from costs and net burn | Recalculate | 10 |
| Missing month | a whole row deleted | Adds the row, copies the company's fixed details (name, sector, deal terms) | Fix | 8 |
| Remaining gaps | the money and headcount values in added rows, blanked headcounts | Interpolates within that company only, marks as estimated | Estimate | 16 rows (32 values) |

The cleaner first checks that all 13 required columns exist and stops with a clear error if any are missing.

### Recalculated vs estimated values

These are deliberately treated differently:

- **Recalculated** values follow exactly from other columns, using the accounting identity below. They're as good as the original. Of the 10 recalculated revenues, all 10 match the truth to within €1.
- **Estimated** values are interpolated: a straight line between the month before and the month after, for the same company. They're educated guesses, so each one is marked with `revenue_estimated`, `cash_estimated` or `headcount_estimated`, and the app and the update show how many estimated values each company has.

Interpolation is done **per company** and **in time order**. Otherwise a gap at the start of one company's data would be filled using the previous company's last month.

### The accounting identity check

Net burn is defined as costs minus revenue, so these three numbers must always agree:

$$
\text{net burn} = \text{costs} - \text{revenue}
\quad\Longleftrightarrow\quad
\text{revenue} = \text{costs} - \text{net burn}
$$

If reported revenue differs from costs − net burn by more than €2 (allowing for rounding), revenue is replaced and the change is logged. This is better than flagging "suspiciously large" values. It needs no arbitrary threshold, it catches errors in **both** directions, and it gives the **correct** value instead of just a warning. Its limitation is that with three linked columns it can tell that a row is wrong, but not which column is wrong. Here it assumes costs and burn are correct.

### Cleaning score against the truth file

Because the data is synthetic, we kept the clean "truth" version (`data/truth_portfolio.csv`) and can measure how well the cleaner did:

| Column | Real values within 1% of truth | Estimated values within 1% | Estimated average error |
|---|---|---|---|
| Revenue | 100% (352 values) | 25% (8 values) | 2.7% |
| Cash | 100% (352 values) | 100% (8 values) | 0.1% |
| Headcount | 100% (344 values) | 81% (16 values) | 0.8% |

Revenue is the hardest to estimate because it has random month-to-month noise of about ±5%, and a straight line can't predict that. Cash is a running total and changes smoothly, so interpolation is almost exact.

### Metrics

Symbols: *t* = latest month, *w* = window in months, *C* = cash, *B* = net burn, *R* = monthly revenue. $\bar{B}_w(t)$ is the average burn over the *w* months ending at month *t*. The formulas below are copied from `FORMULAS` in `src/metrics.py`, which the app displays.

**Net burn**: how much cash the company loses in a month (negative means it made money).

$$
B_t = \text{costs}_t - R_t
$$

**Average burn**: the average monthly net burn over the last *w* months.

$$
\bar{B}_w(t) = \frac{1}{w} \sum_{i=0}^{w-1} B_{t-i}
$$

**Runway**: how many months the current cash lasts at the recent average burn (0 if cash is already gone, infinite if the company isn't burning cash). Averaging over *w* months smooths out one unusual month, while still reflecting how the company spends now.

$$
\text{runway} = \frac{C_t}{\bar{B}_w(t)}
$$

**Monthly growth**: the steady monthly growth rate that would turn revenue *w* months ago into revenue now.

$$
g_w = \left( \frac{R_t}{R_{t-w}} \right)^{1/w} - 1
$$

**Annualised growth**: the yearly growth you get if the monthly rate compounds for 12 months. 5% a month is about 80% a year, not 60%.

$$
g_{\text{year}} = (1 + g_w)^{12} - 1
$$

**Year-on-year growth**: how much revenue changed compared with the same month one year earlier. It's more stable than monthly growth because random noise matters less over 12 months.

$$
\text{YoY} = \frac{R_t}{R_{t-12}} - 1
$$

**Burn trend**: the % change in average burn between the last *w* months and the *w* months before, where a negative value always means burn fell.

$$
\text{trend} = \frac{\bar{B}_w(t) - \bar{B}_w(t-w)}{\left| \bar{B}_w(t-w) \right|} \times 100
$$

**ARR (annual recurring revenue)**: this month's revenue as if it continued for a year.

$$
\text{ARR} = 12 \, R_t
$$

**Burn multiple**: euros of cash burned for each euro of new annual revenue added over the last *w* months (blank and noted "profitable" if the company burned no net cash, or "not growing" if revenue didn't grow). Below 1 is excellent and above 3 is inefficient.

$$
\text{burn multiple} = \frac{\sum_{i=0}^{w-1} B_{t-i}}{12 \, (R_t - R_{t-w})}
$$

If a company has fewer months of history than a metric needs, that metric is left blank instead of failing.

### How flags work

Each company goes through a checklist:

$$
\text{flag} = \begin{cases} \text{red} & \text{if } C_t = 0 \text{ or runway} < r_{\text{red}} \\ \text{amber} & \text{if runway} < r_{\text{amber}} \text{ or trend} > \tau \text{ or burn multiple} > m \\ \text{green} & \text{otherwise} \end{cases}
$$

Red if out of cash or runway is under 6 months; amber if runway is under 12 months, burn rose more than 20%, or the burn multiple is above 3; otherwise green, and the most serious matching rule decides the flag.

- **The worst flag wins.** Risks don't cancel out: four months from running out of cash is urgent however good the other numbers look. Missing a real problem costs far more than checking a false alarm.
- **Every matching rule is listed in the reasons**, with the real numbers, e.g. *"runway 4.8 months (under 6); burn multiple 154.1 (over 3)"*.
- **Green companies get a positive reason** ("profitable" or "runway 40 months (over 12)"), so you can see the checks ran.
- **Estimated values are mentioned but never change the flag.** "Includes 6 estimated values" lowers *confidence*, not *health*.

With the default settings: **5 red** (4 out of cash, plus Vexalune with 4.8 months of runway), **2 amber** (Quandrift, burn up 23%; Nobbleworth, burn up 47%) and **8 green**.

### Fund metrics

Symbols: *V* = valuation, *o* = ownership %, *I* = amount invested, *D* = distributions, *P* = paid-in capital.

**Valuation**: annual revenue run rate times an assumed sector multiple, or 0 if the company has run out of cash.

$$
V = 12 \, R_t \times M_{\text{sector}}
$$

**Stake value**: the fund's share of that valuation.

$$
\text{stake value} = V \times o / 100
$$

**MOIC**: what our stake is worth now (valuation times ownership %) divided by what we invested (*I*), so 2.0 means the money doubled on paper.

$$
\text{MOIC} = \frac{V \times o / 100}{I}
$$

**Paid-in capital**: all the money the fund invested.

$$
P = \sum I
$$

**NAV (net asset value)**: the current value of all stakes together.

$$
\text{NAV} = \sum \text{stake value}
$$

**DPI**: cash actually returned to investors (distributions, *D*) divided by cash they paid in (*P*). Here *D* = 0 because no company has been sold yet.

$$
\text{DPI} = \frac{D}{P}
$$

**TVPI**: total value, unrealised stakes (NAV) plus cash already returned, divided by cash paid in.

$$
\text{TVPI} = \frac{\text{NAV} + D}{P}
$$

**Share of value**: each company's stake as a percentage of NAV. It shows concentration.

$$
\text{share of value} = \frac{\text{stake value}}{\text{NAV}} \times 100
$$

With the default multiples: paid in **€24,700,000**, NAV **€21,781,222**, TVPI **0.88**, DPI **0.00**, 4 companies written off, and the top 2 companies (Fizzlethorpe and Trundlepop) hold **41% of NAV**.

Flags and value answer different questions. Quirrelby is green (40 months of runway) but has a MOIC of 0.08, while Vexalune is red but still valued at €11.7M, because the valuation ignores how close it is to running out.

### Warning backtest

Would the flags have warned us in time? For every month from April 2025, the metrics and flags are recalculated using **only the data available up to that month**. Using later months would mean "knowing the future" and make the test look better than reality.

| Company | First month at €0 cash | First red flag | Months of warning from red | First amber flag (months before €0) |
|---|---|---|---|---|
| Zorblex | Nov 2025 | May 2025 | 6 | Apr 2025 (7, the first month tested) |
| Plonkwick | Apr 2026 | Oct 2025 | 6 | May 2025 (11) |
| Bazzlewick | Jul 2026 | Feb 2026 | 5 | Apr 2025 (15) |
| Krindle | Jun 2026 | Jan 2026 | 5 | Apr 2025 (14) |

All 4 were flagged red before running out, with an average of **5.5 months** of warning.

**Red is a countdown, amber is the early warning.** Red means "runway under 6 months", so a red flag will always come about 6 months before the money runs out. The backtest confirms the runway estimate is accurate, not that red is clever. Bazzlewick and Krindle got only 5 months because their burn kept rising. **Amber** came 11–15 months ahead, early enough to act (raise money, cut costs, find a buyer).

What the backtest doesn't measure is **false alarms**: companies flagged that never ran out. Quandrift and Nobbleworth switch between green and amber, which in real use could cause alert fatigue.

### Limitations

- The 3-month average looks backwards. If burn keeps rising, real runway is shorter than reported.
- Monthly growth over short windows is noisy (Trundlepop shows 17% a month against a true trend of 5–8%).
- Sector multiples are illustrative, and dilution from later funding rounds is ignored, so stake values are likely overstated.
- Startups never raise new money in this data, so nobody recovers.
- The backtest's cleaned data used interpolation, which looks at the month after a gap. That's a small leak of future data (8 estimated rows).

## Risk page: Monte Carlo

### The idea in plain words

Runway gives one number: "4.8 months". But the future isn't one number. Monte Carlo is like asking 1,000 slightly different versions of next year what happens: in some, revenue has a good run, in others a bad one. Then we count how often the company runs out of cash. If 511 of 1,000 versions run out within 18 months, the chance is about 51%.

### The steps

1. **Learn each company's growth and wobble.** From the last 12 months, measure the average monthly % change in revenue and in costs (the growth) and how much it varies from month to month (the wobble, or standard deviation).
2. **Simulate many futures.** For each of 1,000 simulations and each future month, draw a random growth rate around that average and compound it month by month:

$$
R_k = R_{k-1} \times (1 + g_k), \qquad g_k \sim \text{Normal}(\mu, \sigma)
$$

   Cash then falls by each month's burn: $C_k = C_{k-1} - (\text{costs}_k - R_k)$.

3. **Count how often cash hits zero.** The share of simulations where cash reaches €0 at any point is the probability of running out. The typical month it happens is the median "months to zero".

Each company uses its own random seed, so the companies' random luck is independent and the results are reproducible.

### Scenarios and jump events

| Scenario | What changes |
|---|---|
| **Base** | Growth and wobble exactly as learned from history |
| **Slowdown** | Average revenue growth halved |
| **Cost spike** | Costs jump 20% at the start and stay higher |
| **Downturn** | Revenue growth halved, **plus jump events**: each month there's a 5% chance of a sudden 20% revenue drop |

A **jump** is a sudden event like losing a big client. Unlike normal monthly wobble, it doesn't average out: revenue stays lower afterwards. All scenarios use the same random draws, so differences come from the scenario, not from luck.

Probability of running out of cash within 18 months:

| Company | Base | Slowdown | Cost spike | Downturn |
|---|---|---|---|---|
| Quandrift | 51.1% | 93.1% | 100.0% | 96.8% |
| Nobbleworth | 22.0% | 38.6% | 90.5% | 61.8% |
| Vexalune | 100% | 100% | 100% | 100% |
| All green companies | 0% | 0% | 0% | ≤ 0.1% |

Each company is sensitive to something different: Nobbleworth's main risk is **costs**, not revenue.

### Portfolio failures

Counting, in each simulated future, how many companies that still have cash today run out:

| Within 18 months | Base | Downturn |
|---|---|---|
| Expected additional failures | 1.73 | 2.59 |
| At least 1 | 100% | 100% |
| At least 2 | 60% | 98% |
| At least 3 | 13% | 60% |

"At least 1" is always 100% because Vexalune runs out in every simulation. The expected number is simply the sum of the companies' probabilities: 1.00 + 0.511 + 0.220 = 1.73.

### The fan chart and P10 / P50 / P90

The fan chart shows one company's simulated cash month by month:

- **P50 line (median):** half the simulated futures are above it and half below. It's the typical path.
- **Shaded band (P10 to P90):** 80% of futures fall inside it. 10% are below the bottom edge (a bad but plausible outcome) and 10% above the top edge (a good but plausible one).

The band **starts narrow and widens**, because uncertainty compounds over time. When the bottom edge touches €0, at least 10% of futures have run out by that month.

### Limitations

- **Normal noise** ignores fat tails: extreme months happen more often in real life than a bell curve predicts.
- **Independence:** in the base case each company's luck is independent, but a real recession hits many companies at once, so portfolio-wide risk is probably understated.
- **No funding rounds:** nobody raises new money, so a company can only run down its cash.
- Costs grow at a fixed rate in this data, so only revenue is uncertain, and each month's shock is independent of the last.

## Risk page: machine learning

### What the model predicts

For each company and month: **"Will this company run out of cash within the next 6 months?"** The answer is a probability between 0 and 1.

### How the dataset is built

- **One row per company per month** (April 2025 to April 2026), 188 rows in total.
- **Features** (inputs), all calculated using **only data up to that month**: runway (capped at 36 months), monthly growth, burn trend, and whether the company is profitable.
- **Label** (the answer): 1 if the company's cash hits €0 in any of the next 6 months, otherwise 0. This is the only column that looks into the future, because it's the thing we want to predict.
- Rows are **removed** when the company is already out of cash (nothing left to predict), when the 6-month window goes past the end of the data (answer unknown), or when a feature is missing.

### Why whole companies are left out during testing

A company's consecutive months are almost copies of each other. If June was used for training and July for testing, the model would just recognise the company. So testing uses **leave-one-company-out**: train on 14 companies, predict the 15th, and repeat for every company. Every prediction is for a company the model has never seen.

### Why accuracy is misleading

Only **21 of 188 rows** (11%) are "runs out within 6 months", against **167** that aren't. A "model" that always says "won't run out" is right 167 / 188 = **88.8%** of the time, and it never catches a single failure. So we use two better measures:

$$
\text{precision} = \frac{\text{caught}}{\text{caught} + \text{false alarms}}
\qquad
\text{recall} = \frac{\text{caught}}{\text{caught} + \text{missed}}
$$

- **Precision:** of the companies we flagged, how many really ran out?
- **Recall:** of the companies that ran out, how many did we flag?

Both models use `class_weight="balanced"`, so a missed failure counts as much as all the survivors together, and the model can't score well by always saying "safe".

### The two models in plain words

- **Logistic regression** gives each feature a weight, adds them up, and squeezes the total into a probability with an S-shaped curve (the sigmoid). It's simple and easy to interpret: the runway weight is −3.9, and every other feature is close to 0.
- **Random forest** builds 200 small decision trees ("Is runway under 7.8 months? Is burn rising?"), each on a slightly different random sample, and averages their votes. It can learn combined rules like "short runway **and** rising burn". Each tree asks at most 3 questions (`max_depth=3`), so it can't memorise the 4 failing companies.

### Results against the rule baselines

At the 0.5 threshold, using leave-one-company-out predictions:

| Detector | Precision | Recall | Caught | False alarms |
|---|---|---|---|---|
| Rule: red (runway < 6) | 1.00 | 0.90 | 19 of 21 | 0 |
| Rule: red or amber | 0.31 | 1.00 | 21 of 21 | 46 |
| Logistic regression | 0.66 | 1.00 | 21 of 21 | 11 |
| Random forest | 0.91 | 1.00 | 21 of 21 | 2 |

- The red rule never raises a false alarm but missed 2: Bazzlewick and Krindle had runways just above 6 months while their burn was rising.
- Logistic regression's 11 "false alarms" are all early warnings: failing companies flagged 7–10 months ahead, just outside the 6-month label.
- The random forest separates best here, but with only 4 failing companies the difference between 11 and 2 false alarms is fragile.

Feature importance (random forest): runway 0.76, burn trend 0.16, monthly growth 0.08, profitable 0.00. This shows what the model *used*, not what *causes* failure.

**Risk today:** Vexalune has a **91%** ML risk and a **100%** Monte Carlo probability of running out within 6 months. Two completely different methods agree. Every other company is near 0%.

### The threshold trade-off

The model gives a probability, and the threshold decides when that becomes a warning. A lower threshold catches more failures but raises more false alarms. A higher one does the opposite. For a fund, a missed failure costs far more than a false alarm, which argues for a lower threshold.

### Controls

| Control | Options | Default | Try this |
|---|---|---|---|
| **Model** | Logistic regression, Random forest | Logistic regression | Switch to **Random forest**: false alarms drop from 11 to 2, and it still catches 21 of 21. |
| **Probability threshold** | 0.10–0.90, steps of 0.05 | 0.50 | With logistic regression, set **0.30**: false alarms rise to 17. Set **0.70**: they fall to 7, still catching all 21. With the random forest, set **0.75**: 0 false alarms, but it now catches only 20 of 21. |

### Caveats

- **Synthetic data**, generated with clear "strong / steady / struggling" profiles, so it's easier than real data.
- **Only 4 companies ever ran out**, so the model learns from very few events.
- **The models mostly rely on runway.** The label ("out of cash within 6 months") is closely tied to runway by construction, so ML mainly confirms the runway rule and places the threshold better.
- **ML always uses a 3-month window**, whatever the Portfolio page slider says.

## Update page

The Update page writes the monthly portfolio update as text you can read, download, or paste into an email. Section by section:

1. **Title:** "Portfolio update: October 2026" (the latest month in the data).
2. **Summary line:** Needs attention: 1 · Watch: 2 · Written off: 4 · Flag changes: 3.
3. **Fund snapshot:** paid in, NAV, TVPI, DPI (with "no exits yet") and the top 2 companies' share of NAV.
4. **Needs attention:** red companies that still have cash, with their reasons and Monte Carlo probability, e.g. *🔴 **Vexalune** (SaaS): runway 4.8 months; burn multiple 154.1; 100% chance of running out within 18 months (Monte Carlo).*
5. **Watch:** amber companies, with reasons and Monte Carlo probability.
6. **Doing well:** green companies with a short positive reason ("profitable", "runway over 36 months").
7. **Written off:** companies with no cash left: "out of cash."
8. **Flag changes since last month:** e.g. Vexalune 🟠 → 🔴, Quirrelby 🟠 → 🟢, Nobbleworth 🟢 → 🟠.
9. **Data quality:** the number of cleaning fixes per issue type, and which companies' metrics rely on estimated values (e.g. Snorvik: 7).
10. **Assumptions:** synthetic data, illustrative multiples, dilution ignored, normal noise, independent companies.

**It's generated from fixed templates and calculated numbers, not by AI.** The same data always produces exactly the same sentences, and every word traces back to a calculation.

## Pension page

### The pension promise

A fictional Austrian company promises a **defined benefit pension**. From age 65, every year for life:

$$
\text{pension} = 1\% \times \text{years of service} \times \text{final yearly salary}
$$

In Austria, employees are normally paid **14 monthly salaries a year**: 12 regular ones plus a holiday bonus (around June) and a Christmas bonus (around November), set by collective agreements. So:

$$
\text{yearly salary} = \text{monthly salary} \times 14
$$

Using × 12 would understate every pension by 14%. Example: 30 years of service and a final monthly salary of €5,000 gives 0.01 × 30 × €5,000 × 14 = **€21,000 a year**.

### Data validation and client queries

The employee file (43 rows) is checked before any valuation:

| Check | What happens | Count |
|---|---|---|
| Exact duplicate | Dropped and logged | 2 |
| Salary as Austrian text (`€5.650,00`) | Converted and logged (this is a format, not a guess) | 4 |
| Entry date before birth date | **Client query**: "dates possibly swapped, please confirm" | 2 |
| Entry age under 15 | **Client query**: "please confirm the entry date" | 2 |
| Missing salary | **Client query**: "please provide the current gross monthly salary" | 3 |
| Age 65 or over | **Client query**: "still working, receiving a pension, or left?" | 1 |

Result: **33 valid employees** and **8 client queries**, which you can download as a CSV and send to the client.

**Why query instead of estimate?** In the portfolio, a missing month sits between two real months of the same company, so interpolation borrows real information. An employee record has no neighbours. A guessed birth date or salary would directly change that person's pension, and only the client knows the real value. An actuary who signs off the result can defend "we asked", but not "we guessed".

### The projected unit credit chain, step by step

**Projected unit credit (PUC)** is the method required by IAS 19. It counts only the service **already worked**, but values it at the salary expected **at retirement**, because the plan pays on final salary.

Symbols: *x* = age today, *n* = years to retirement (65 − *x*), *s* = salary growth, *i* = discount rate.

**1. Yearly salary**

$$
S = \text{monthly salary} \times 14
$$

**2. Projected final salary**, compounded until retirement:

$$
S_{65} = S \times (1 + s)^{n}
$$

**3. Earned pension**: only the years worked so far count.

$$
E = \text{accrual rate} \times \text{past service} \times S_{65}
$$

**4. Mortality (Makeham)**: the chance of dying within one year at age *x*. *A* is a constant risk (accidents), and $B c^x$ grows 9.5% per year of age. The mortality factor scales it.

$$
q_x = \text{mortality factor} \times \left( A + B \cdot c^{x} \right), \qquad A = 0.0002,\; B = 0.000035,\; c = 1.095
$$

**5. Survival**: to reach 65 you must survive every year in between, so the probabilities multiply.

$$
{}_{n}p_{x} = \prod_{k=0}^{n-1} \left( 1 - q_{x+k} \right)
$$

**6. Discount factor**: €1 paid *n* years from now is worth less today, because money set aside can earn interest.

$$
v = \frac{1}{1+i}, \qquad \text{discount factor} = v^{n}
$$

**7. Annuity factor**: today's value, at 65, of €1 a year for life, paid at the start of each year until age 110 at most.

$$
\ddot{a}_{65} = \sum_{k=0}^{45} v^{k} \cdot {}_{k}p_{65}
$$

With these assumptions, $\ddot{a}_{65} = 13.85$. That's less than the roughly 19 years of life expectancy at 65, because later payments are discounted.

**8. DBO (defined benefit obligation)**: what the company owes today for service already worked.

$$
\text{DBO} = E \times \ddot{a}_{65} \times v^{n} \times {}_{n}p_{x}
$$

### Worked example: employee E017

| Step | Calculation | Result |
|---|---|---|
| Age at 31.12.2026 | | 44.74 years |
| Past service | | 13.85 years |
| Years to retirement | 65 − 44.74 | 20.26 |
| Yearly salary | €3,250 × 14 | €45,500 |
| Projected final salary | €45,500 × 1.025^20.26 | €75,039 |
| Earned pension per year | 0.01 × 13.85 × €75,039 | €10,391 |
| Annuity factor at 65 | | 13.8523 |
| Discount factor | 1 / 1.035^20.26 | 0.4981 |
| Survival to 65 | | 0.8891 |
| **DBO** | €10,391 × 13.8523 × 0.4981 × 0.8891 | **€63,742** |

In words: E017 has earned a pension of €10,391 a year. At 65 that stream is worth about €143,900 as a lump sum. Bringing it back 20 years (× 0.498) and allowing for the chance of not reaching 65 (× 0.889) gives €63,742 today. The app shows these steps for any employee you select.

### Sensitivities, duration and convexity

Changing one assumption at a time:

| Scenario | Total DBO | Change |
|---|---|---|
| Base | €2,821,996 | |
| Discount rate −0.5% | €3,163,670 | +12.1% |
| Discount rate +0.5% | €2,526,926 | −10.5% |
| Salary growth +0.5% | €3,022,107 | +7.1% |
| Salary growth −0.5% | €2,639,575 | −6.5% |
| Mortality × 0.9 | €2,936,460 | +4.1% |

**Why a lower discount rate increases the DBO:** if money set aside earns less, you need more of it today to cover the same future payments. The payments are decades away, so the effect compounds: €1 due in 30 years is worth €0.31 today at 4%, but €0.41 at 3%.

**Duration** is the % change in DBO for a 1 percentage point change in the discount rate:

$$
\text{duration} = \frac{\text{DBO}_{-0.5\%} - \text{DBO}_{+0.5\%}}{2 \times \text{DBO}_{\text{base}} \times 0.005}
$$

Here it's **22.6 years**: a 1-point drop in rates raises the DBO by about 22.6% (about €640,000). It's also roughly the average time until the pension money is paid. It's long here because all employees are still working.

**Convexity:** a rate cut raises the DBO more (+12.1%) than an equal rate rise lowers it (−10.5%), because discounting is a curve, not a straight line. Duration uses both sides to average this out.

### Assumption Monte Carlo

Instead of one discount rate and one salary growth rate, 500 combinations are drawn (each normally distributed around its base value, standard deviation 0.5 points), and the DBO is recalculated for each:

| | Total DBO |
|---|---|
| P10 | €2,382,787 |
| P50 | €2,818,842 |
| P90 | €3,305,031 |

In 80% of draws the DBO lies between €2.38M and €3.31M, about ±16% around the base. A single number hides that.

### Limitations

- **Mortality is illustrative** (Makeham). A real Austrian valuation would use the official **AVÖ 2018-P** tables, separate for men and women.
- **No turnover:** nobody leaves before 65, and there are no death benefits before retirement. Both make the DBO higher than reality.
- **Only the DBO**, with no service cost or interest cost (the yearly changes IAS 19 reporting also needs).
- **Independent draws:** discount rate and salary growth are drawn independently, but in reality both move with inflation and partly cancel out, so the Monte Carlo range is probably too wide.
- Employees with open client queries aren't valued, so the total is incomplete until the client answers.
- Only active employees are valued, not pensioners.

## Assumptions and limitations

- **All data is synthetic**, with fictional companies and employees, and generated with clear profiles that make patterns easier to find than in real data.
- **Startups never raise new money**, and companies at €0 keep reporting costs.
- **Sector multiples are illustrative**, not market data. **Dilution is ignored**, so stake values are likely overstated.
- **DPI is 0** because no company has been sold. TVPI is entirely paper value.
- **Runway uses a backward-looking average**, so it overstates runway when burn is rising.
- **Estimated values** are interpolated and marked. Interpolation uses the month after a gap, a small look-ahead in the backtest.
- **Monte Carlo** uses normal noise (no fat tails), treats companies independently in the base case, has jumps only in the downturn scenario, and doesn't model funding rounds.
- **Machine learning** learns from only 4 failed companies, relies mostly on runway, and always uses a 3-month window.
- **Pension mortality** is illustrative Makeham, not AVÖ 2018-P. There's no turnover, no service or interest cost, and no pensioners, and discount rate and salary growth are drawn independently although they're linked through inflation.

## Glossary

| Term | Meaning |
|---|---|
| **ARR** | Annual recurring revenue: monthly revenue × 12, as if this month's revenue continued all year. |
| **MRR** | Monthly recurring revenue: revenue earned in one month from ongoing customers. This project's monthly revenue plays this role. |
| **MoM** | Month on month: the change compared with the previous month. |
| **YoY** | Year on year: the change compared with the same month a year earlier. |
| **MOIC** | Multiple on invested capital: current value of a stake ÷ amount invested. 2.0 means the money doubled on paper. |
| **NAV** | Net asset value: the current estimated value of all the fund's stakes. |
| **DPI** | Distributions to paid-in: cash returned to investors ÷ cash they put in. It only counts real cash. |
| **TVPI** | Total value to paid-in: (NAV + distributions) ÷ paid-in. It includes paper value. |
| **IRR** | Internal rate of return: the yearly return that accounts for *when* money went in and came out. Not calculated here. |
| **VC** | Venture capital: investing in young, fast-growing companies in exchange for ownership. |
| **LP** | Limited partner: an investor in a VC fund (e.g. a pension fund) who provides the money. |
| **GP** | General partner: the VC firm that manages the fund and picks the investments. |
| **DBO** | Defined benefit obligation: today's value of the pension a company has promised for service already worked. |
| **PUC** | Projected unit credit: the method for the DBO that counts past service only but uses the projected final salary. |
| **IAS 19** | The international accounting standard for employee benefits, including pensions. |
| **Runway** | How many months a company's cash lasts at its current burn rate. |
| **Net burn** | Costs minus revenue in a month: the cash a company loses. Negative means it made money. |
| **Burn multiple** | Cash burned ÷ new annual revenue added. Below 1 is excellent, above 3 is inefficient. |
| **P10 / P50 / P90** | Percentiles: 10% of outcomes are below P10, half are below P50 (the median), 90% are below P90. |
| **Precision** | Of everything flagged, the share that really happened. |
| **Recall** | Of everything that really happened, the share that was flagged. |
